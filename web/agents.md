# Web 开发约定（React + TypeScript + Vite）

本文件只约束 `web/` 目录。技术栈以当前 `package.json` 为准：React 19、TypeScript 6、Vite 8；计划引入 Tailwind CSS、shadcn/ui、TanStack Query、TanStack Router、TanStack Table。产品定位与实现范围见 `docs/implementation-plan.md`。

## 技术栈使用原则

1. 不重复造轮子：新增组件、请求方法、工具函数前，先检查 `components/`、`services/`、`shared/` 是否已有可复用实现。
2. 服务端状态统一交给 TanStack Query，本地 UI 状态用 Context 或 Zustand；不要为每个页面单独建状态文件，统一由对应 feature 的 service 管理请求与状态。
3. 表单使用 `react-hook-form` + `zod`，校验规则在边界定义，错误信息直接面向用户；不要在提交处理函数里手写逐字段判断。
4. 路由使用 TanStack Router，页面按 `features/` 组织，路由声明集中在 `routes/`，不要在组件内部散落路径字符串。
5. 表格使用 TanStack Table，列宽按固定像素或 `rem` 定义，最后一列吸收剩余空间，避免业务列被拉伸；分页固定在表格下方，滚动时保持可见。

## 视觉与交互设计

Veristack 面向专业交付场景，界面必须现代化、精致、美观，传达「可信、严谨、专业」的产品气质，避免模板化后台管理系统的观感。

1. **视觉基调**：对标 Trae、CodeBuddy 等主流 Agent Web 端以及 ChatGPT 网页的设计感——大面积留白、克制的中性色、清晰的信息层级、精确的间距与圆角、轻量阴影与细腻过渡。靠排版与空间关系建立秩序，而非粗边框和强色块；同一屏内只突出一个主要操作。
2. **明暗双主题**：必须同时支持浅色与深色两套配色。颜色统一通过语义化 CSS 变量（如 `--surface`、`--foreground`、`--border`、`--accent`）定义，组件内禁止写死色值；主题选择持久化到本地并在首屏加载时生效，避免闪烁。两套主题都要满足 WCAG AA 对比度，状态色（成功、警告、错误、进行中）在两套主题下均可辨识。
3. **复杂组件双主题验证**：图表、时间线、证据缩略图等组件必须在浅色与深色两套主题下逐一验证，禁止只在默认主题下检查。
4. **图标与字体**：图标风格统一（线性、同尺寸、同视觉重量），禁止混用不同风格图标库；中文字体使用系统无衬线字体栈，数字与代码使用等宽字体，保证信息密度与可读性。
5. **关键界面语义**：项目概览突出待确认变更与待验收交付；基线对比用并排或逐条高亮展示差异并明确标记冻结版本；交付证据以时间轴串联 Git、CI、截图与测试报告；客户验收门户面向非技术用户，步骤清晰、文案通俗。
6. **状态与反馈**：空状态提供指导性文案，加载态使用骨架屏，禁止空白页面或生硬提示；关键写操作（冻结基线、提交验收、确认交付）必须有二次确认与明确结果反馈。表单错误紧邻字段展示，不用 toast 代替内联校验提示。
7. **动效克制**：过渡动画控制在 150～250ms，仅用于状态变化与层级切换，不做装饰性动画。

## 命名规范

1. 变量、方法、字段命名要让第一次读代码的人无需询问即可理解，除非名称特别长，否则不使用缩写。
2. V 层触发的 C 层事件处理方法统一以 `on` 开头，例如 `onEdit(project)`、`onRowClick(event)`；组件声明、模板绑定与内部调用保持一致。纯展示用的读取数据方法不属于事件处理方法。
3. 请求函数以动词开头，如 `listProjects`、`createDelivery`、`submitAcceptance`；类型以 `Request`、`Response`、`Item` 等后缀区分用途。
4. 文件名使用小写中划线（kebab-case），组件名使用大驼峰（PascalCase），常量使用大写下划线。

## TypeScript 规范

1. 所有文件必须补齐类型定义，禁止使用 `any`；无法确定时使用 `unknown` 并在边界处收窄。
2. 开启严格模式，`noUnusedLocals`、`noUnusedParameters` 保持开启；禁止通过 `@ts-ignore` 绕过类型检查。
3. API 响应、请求参数、枚举值统一在 `services/` 或 `shared/types/` 定义一份，禁止在不同页面重复声明同名结构。
4. 对象字段与类型成员按名称字母升序排列，便于查找与 review。

## 注释规范

1. 新建文件或方法时添加注释，注释核心是说明它解决了什么需求，而不是复述文件名、方法名或实现步骤。
2. 文件使用文件级 JSDoc 说明职责，方法使用多行 JSDoc 放在声明上方，内部用 `-` 逐条描述关键决策。
3. 解释「为什么这么做」，例如为何选择版本化基线、为何在边界校验；不要逐行翻译代码。
4. 新增依赖时注明用途；代码中的数字提取为具名常量，禁止散落魔法数字。

## 组件与样式

1. 优先使用 Tailwind 工具类和 shadcn/ui 组件，除非非常必要，不写自定义 CSS；色值一律走语义化 CSS 变量，与「视觉与交互设计」章节保持一致。
2. Select、Radio、DatePicker 等表单控件先检查 `components/ui/` 是否已有封装；没有则新建共享组件后引用，禁止在业务页面里重复实现。
3. 组件保持单一职责，方法行数以 30 行为宜，最长不超过 40 行；超出时拆分自定义 Hook 或子组件。
4. 自定义 Hook 以 `use` 开头，只封装一个明确的关注点，不承载整页业务逻辑。
5. 列表页、详情页、表单页使用统一布局组件；响应式适配移动端，不依赖桌面宽屏假设。

## 数据与权限

1. 所有请求统一走 `services/` 中的 API 客户端，不在组件里直接调用 `fetch` 或 `axios`。
2. 用户角色与资源归属判断从服务端返回的领域数据读取，前端只做展示与交互控制，不作为最终权限依据。
3. 外部输入（URL 参数、表单、文件上传）在边界校验后才进入业务逻辑；校验失败以用户可理解的错误提示呈现。
4. 时间统一在 `shared/utils/datetime.ts` 的格式化函数中处理，显式使用 `Asia/Shanghai`，禁止依赖浏览器默认时区。

## 工程约束

1. 遵循开闭原则：新增功能尽量通过新增文件与扩展点完成，不大改已有接口和公共组件。
2. 单元测试：`shared/lib`、状态映射、服务层纯函数与表单校验等业务逻辑必须附带单元测试，判定清单见 [`docs/unit-test.md`](../docs/unit-test.md)。纯展示组件豁免。
3. 不允许使用 MCP 自行打开浏览器做测试或验证。
4. 提交前运行 `npm run lint` 与 `npm run build`，确保规范与类型检查全部通过；前端测试框架接入后再补跑 `npm run test`。
