# Evidence Pack 格式契约（版本 2）

Evidence Pack 是一份可以脱离 Veristack 服务端独立核验的交付证据快照。客户或第三方拿到 Pack 后，无需信任服务端，也能确认交付内容是否被篡改。

本契约独立版本化，未来允许其他实现产出兼容的 Pack。

## 一、版本 2 相对版本 1 的变化

版本 1 的签名只覆盖交付清单摘要（`manifestSha256`），`pack.json` 中的附件清单与交付信息未被签名保护。
**这意味着从 `files` 中删除一条记录，核验仍会通过** —— 证据附件可以被合法地抹掉。

版本 2 修正了这一点：

| 变化 | 说明 |
| --- | --- |
| 签名覆盖范围扩大 | 签名载荷包含交付信息、清单引用、**全部附件条目**、签发主体、生成时间与格式版本 |
| 清单引用结构化 | `manifestSha256` 改为 `manifest: { path, sha256 }` |
| 增加签发主体 | 新增 `issuer: { organizationId, keyId }`，使签名来源可被独立识别 |
| 版本校验 | 未知 `schemaVersion` 一律拒绝核验；v1 格式会明确提示签名覆盖不完整 |
| 导出不覆盖历史 | 每次导出分配独立目录，临时目录校验通过后原子发布 |

> v1 格式的 Pack 仍然可以读取，但签名核验会**判定为不通过**并提示重新导出。这是刻意的 Fail Closed 设计。

## 二、目录结构

```
<pack-root>/
├── pack.json          # 元数据：交付信息、清单引用、附件清单、签发主体与签名
├── manifest.json      # 交付清单快照，与交付创建时冻结的内容一致
└── files/             # 证据附件，文件名即内容摘要
    ├── <sha256>.png
    └── <sha256>.xml
```

## 三、pack.json

```json
{
  "schemaVersion": "2",
  "generatedAt": "2026-11-25T10:00:00+08:00",
  "delivery": {
    "baselineVersion": 2,
    "buildNo": "b-202",
    "gitRef": "abc1234",
    "id": "78951c02-3178-4763-b061-2fd16dab996f",
    "projectName": "官网改版",
    "version": 1
  },
  "manifest": {
    "path": "manifest.json",
    "sha256": "a08b27008e6aaae1..."
  },
  "files": [
    {
      "evidenceId": "6f1c...",
      "path": "files/8d3a....png",
      "sha256": "8d3a...",
      "size": 20480,
      "title": "首页深色模式截图"
    }
  ],
  "issuer": {
    "keyId": "abcdef0123456789",
    "organizationId": "6b2c..."
  },
  "signature": {
    "algorithm": "ed25519",
    "publicKey": "BASE64",
    "value": "BASE64"
  }
}
```

### 字段说明

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `schemaVersion` | string | 是 | 格式版本，当前为 `2` |
| `generatedAt` | string | 是 | 生成时间，上海时区 |
| `delivery` | object | 是 | 交付版本基本信息 |
| `manifest` | object | 是 | 交付清单引用，含相对路径与摘要 |
| `files` | array | 是 | 证据附件清单，顺序与内容均受签名保护 |
| `issuer` | object | 是 | 签发主体，含组织 ID 与公钥指纹 |
| `signature` | object | 否 | 清单签名，未配置签名私钥时为空 |

### 文件条目

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `evidenceId` | string | 证据 ID，便于回溯服务端记录 |
| `path` | string | Pack 内相对路径，使用正斜杠分隔，**不得包含 `..`** |
| `sha256` | string | 文件内容摘要 |
| `size` | number | 文件字节数 |
| `title` | string | 证据标题 |

## 四、manifest.json

内容与交付版本创建时冻结的交付清单完全一致，是不可覆盖的快照。典型结构：

```json
{
  "baselineVersion": 2,
  "criteria": [
    {
      "description": "首页加载小于 2 秒",
      "key": "REQ-001::0",
      "requirementCode": "REQ-001"
    }
  ],
  "gitRef": "abc1234",
  "projectName": "官网改版",
  "requirements": [
    {
      "code": "REQ-001",
      "criteria": [{ "description": "首页加载小于 2 秒", "key": "REQ-001::0", "requirementCode": "REQ-001" }],
      "description": "首页需支持主题切换",
      "priority": "high",
      "title": "首页主题"
    }
  ],
  "version": 1
}
```

验收条件的 `key` 是稳定标识，格式为 `需求编号::序号`，客户逐条验收的裁定结果通过该键关联。

## 五、签名

签名算法为 Ed25519。

### 签名载荷

签名对象是**除 `signature` 之外全部元数据**的规范化 JSON：

```json
{
  "delivery": { ... },
  "files": [ ... ],
  "generatedAt": "...",
  "issuer": { ... },
  "manifest": { ... },
  "schemaVersion": "2"
}
```

规范化规则：键名按字典序排列后序列化（Go 实现使用 `map[string]any` 交给 `encoding/json`，后者保证键有序）。
**载荷的键集合与结构属于契约的一部分**，实现方必须严格按此构造，否则验签不通过。

### 签名与验签流程

```
规范载荷
    |
    v
规范化序列化（键名字典序）
    |
    v
Ed25519 Sign / Verify
    |
    v
signature.value
```

因此以下操作都会导致验签失败：

- 删除或新增 `files` 中的任一条目
- 修改交付信息、清单摘要、签发主体或生成时间
- 修改 `schemaVersion`
- 修改 `pack.json` 中除 `signature` 外的任意字段

### 公钥信任

Pack 自带的 `signature.publicKey` 只能证明**内容未被改动**，不能证明**是谁签的**。
要让客户识别签名主体，需要通过独立可信渠道绑定公钥：

- 客户预先固定组织公钥（推荐，成本最低）
- 组织公钥注册信息或可信证书
- 线下交付公钥指纹（`issuer.keyId`）并人工比对

> 这是版本 2 之后仍需由使用方建立的信任关系，Pack 本身无法自证。

## 六、核验流程

使用官方 CLI：

```bash
veristack verify ./delivery-pack
```

输出示例：

```
交付：官网改版 v1（基线 v2）
清单摘要：a08b27008e6aaae1...

[通过] Pack 格式版本：格式版本 2
[通过] 交付清单摘要：清单内容与元数据一致
[通过] 证据附件 files/8d3a....png：附件内容与元数据一致
[通过] 交付清单签名：签名有效，已覆盖交付信息、清单与全部附件

结论：全部核验通过，交付内容与签名均有效
```

CLI 在任一核验项失败时返回非零退出码，便于接入流水线做自动卡口。

### 核验的安全约束

CLI 按处理**不可信输入**的标准设计：

- 只接受规范化后的相对路径，拒绝 `..` 路径段与绝对路径
- 解析后的最终路径必须位于 Pack 根目录之内
- 符号链接解析后仍须位于根目录之内
- 单个附件上限 512 MB，整份 Pack 上限 2 GB，附件数量上限 5000
- 采用流式摘要计算，不把大文件整体读入内存
- 拒绝重复的附件路径
- 未知 `schemaVersion` 一律拒绝

自行实现核验时，参考 `api/internal/platform/pack/verify.go`。

## 七、兼容性

- 版本 2 相对版本 1 是**破坏性变更**（签名语义、字段结构均改变）
- 新增字段属于向后兼容变更，`schemaVersion` 不变
- 改变签名载荷的键集合或结构属于破坏性变更，必须提升 `schemaVersion` 主版本号
- `schemaVersion` 使用「主版本.次版本」形式，当前为 `2`
- 核验方应拒绝未知版本，不得按已知版本的规则猜测处理
