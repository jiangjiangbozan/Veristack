**已实测跑通的四条业务链路**

1. 注册 → 创建项目 → 冻结基线 v1 → 发起变更 → 客户批准 → 生成 v2（v1 未改写）
2. 创建交付 → 冻结清单 → 登记证据 → 生成客户链接 → 逐条裁定 → 提异议 → 开发者回复 → 客户关闭
3. Webhook 接收 → Outbox 消费 → 提交按 `REQ-xxx` 关联需求 → 自动生成 git_commit 证据
4. 导出 Evidence Pack → CLI 离线核验通过 → 篡改后摘要与签名双失败（退出码 1）

**成熟度判断**：核心业务骨架完整，已远超原型阶段。但**证据完整性与身份可信度**存在 P0 级缺陷，当前不能商用。

## 二、P0 · 信任与数据安全（阻塞商用）

这一组不修复，产品核心卖点不成立。审查报告判断正确，我已逐条核实代码位置。

### P0-1 Evidence Pack 签名范围不完整 🔧

- **位置**：`api/internal/platform/pack/verify.go` → `verifySignature`
- **现状**：签名对象仅为 `meta.ManifestSHA`，`pack.json` 中的 `files[]` 与 `delivery` 字段未被签名覆盖
- **后果**：从 `files[]` 中删除任一条目，核验依然通过 —— **证据附件可被「合法地」从证据包中抹掉**
- **修复**：升级 Evidence Pack v2，对规范化签名载荷签名：

  ```
  { schemaVersion, delivery, manifest{path,sha256}, evidence[]{id,path,sha256,size,title}, generatedAt, issuer{organizationId,keyId} }
  ```

  规范化序列化 → SHA-256 → Ed25519 Sign
- **附带**：公钥不能只信 Pack 自带，需支持「客户预先固定组织公钥」的独立绑定
- **验收**：修改、删除、替换签名范围内任一数据，独立核验必须失败
- **影响文件**：`api/contracts/evidence-pack/v1.md`（→ v2）、`platform/pack/pack.go`、`verify.go`、`cmd/veristack`

### P0-2 分享令牌明文写入审计 🔧

- **位置**：`api/internal/acceptance/handler.go` → `createShareToken`
- **现状**：`recordAudit(..., map[string]string{"token": token})`，而 `audit.Writer.Record` 会把 `after` JSON 序列化后落库
- **后果**：`share_tokens` 表只存哈希的安全设计被完全绕过 —— 数据库泄露即等于**所有客户验收链接泄露**
- **修复**：审计只记录 `tokenIssued: true` 与 `expiresAt`，绝不记录令牌本身
- **附带**：需一次性订正脚本清理历史审计记录 + 撤销已签发链接
- **验收**：在审计表中检索不到任何令牌明文

### P0-3 Evidence Pack 路径穿越 🔧

- **位置**：`api/internal/platform/pack/verify.go:82`
- **现状**：`filepath.Join(root, filepath.FromSlash(file.Path))`，未约束解析后路径必须位于 Pack 根目录内
- **后果**：恶意构造的 Pack 可让 CLI 读取 Pack 目录**之外**的本地文件
- **修复清单**：
  - 只接受规范化后的相对路径，拒绝 `..` 路径段与绝对路径
  - 解析后校验最终路径确实位于 Pack 根目录之内
  - 防止符号链接逃逸
  - 限制单个附件与整个 Pack 的总体积
  - 改用流式哈希，避免超大文件占满内存
  - 拒绝重复附件路径与无效 schemaVersion
- **验收**：构造含 `../../etc/passwd` 类路径的 Pack，CLI 必须拒绝且不读取目标文件

### P0-4 客户邮箱身份未验证 🔧

- **位置**：`api/internal/acceptance/service.go` → `EnsureCustomer`
- **现状**：
  - 邮箱不存在 → 直接创建客户账号（随机密码），邮箱归属从未验证
  - 邮箱已存在 → 直接返回该用户，**未校验其组织归属**
- **后果**：
  1. 持有分享链接者输入任意邮箱，即可以该身份提交验收结论
  2. 更严重：可冒用**其他组织**已有用户身份（`users_email_active_key` 是全局唯一索引，邮箱全局唯一）
- **修复**：邮箱 OTP 验证流程；验证通过后落为「已验证邮箱」身份
- **验收**：未验证邮箱提交裁定被拒绝；跨组织邮箱被拒绝

### P0-5 审计写入失败被忽略 🔧

- **现状**：全项目使用 `_ = writer.Record(...)`，审计失败时业务操作仍返回成功
- **后果**：状态已改但审计缺失 —— **这正是产品要解决的核心问题本身**
- **修复**：关键写操作与审计事件在同一事务内写入；审计写失败则业务变更回滚
- **验收**：构造审计写入失败场景，业务变更不得静默成功

### P0-6 签名私钥加载失败静默降级 🔧

- **位置**：`api/cmd/server/main.go` → `loadSigningKey`
- **现状**：读取失败仅 `log.Error` 并返回 `nil`，服务继续以「不签名」模式运行
- **修复**：配置了私钥路径就必须加载成功，否则**启动失败**（Fail Closed）

### P0-7 默认密钥未被拒绝 🔧

- **位置**：`api/internal/platform/config/config.go` → `Validate`（仅校验非空）
- **现状**：`.env.example` 与 Compose 提供 `change-me-in-production`，未修改也能正常启动
- **修复**：拒绝已知默认值；强制最小熵校验

## 三、P1 · 完整业务闭环

### P1-1 Pack 导出会覆盖历史 ✅

- **位置**：`api/internal/delivery/service.go:181` → `os.RemoveAll(root)`
- **现状**：每次导出删除旧目录并用当前数据库数据重建同一交付目录
- **冲突点**：与「证据快照不可覆盖」的产品设计直接矛盾
- **修复**：每次导出分配独立 Export ID；先写临时目录，完整校验后原子发布；绝不覆盖历史导出

### P1-2 Webhook 缺少幂等键 ✅

- **位置**：`evidence_items` 表无任何针对提交 SHA 的唯一约束
- **现状**：同一 Webhook 重复投递 → 同一 Commit 生成多条重复证据（我本地实测已产生 2 条相同提交记录）
- **修复**：基于第三方事件 ID 或 Commit SHA 建立幂等约束；补充重复投递测试

### P1-3 S3 配置被接受但程序始终使用本地盘 ✅

- **位置**：`api/cmd/server/main.go` 恒用 `&storage.LocalStore{...}`，而 `config.Validate` 接受 `driver=s3`
- **后果**：配置了 S3 会**静默落到本地盘**，运维误判数据已上云
- **修复**：实现 S3 工厂；或在实现前直接拒绝 `s3` 配置值（Fail Closed）

### P1-4 审计事件写了却查不到 ✅

- **原状**：`audit_events` 表与查询都存在，但没有任何接口暴露
- **已修复**：新增交付审计查询接口与前端时间线，合并交付、导出与客户分享事件

### P1-5 健康检查只有存活检查 ✅

- **原状**：`/healthz` 静态返回 `ok`，不检查数据库
- **已修复**：新增 `/readyz`，2 秒超时 Ping 数据库，失败返回 503

### P1-6 Pack 下载地址指向未注册接口 ✅

- **原状**：下载地址指向从未注册的路由，前端点击必然 404
- **已修复**：导出返回 `exportId`，新增 ZIP 下载接口，归档时拒绝符号链接与越界路径

### P1-7 OpenAPI 契约与实现不一致 ✅

## 九、建议执行顺序

不要同时开十条分支，按依赖关系推进。

### 第一批：可信性修复（全部 🔧，无外部依赖）

1. P0-2 分享令牌明文 → 审计
2. P0-3 Pack 路径穿越
3. P0-1 Evidence Pack v2 签名载荷
4. P0-5 审计事务化
5. P0-4 客户邮箱验证（含 P2-6 邮件通道，需 SMTP 配置）
6. P0-6 签名私钥 Fail Closed
7. P0-7 默认密钥拒绝
8. P1-1 Pack 导出版本化
9. P1-2 Webhook 幂等
10. P1-3 S3 配置 Fail Closed

> **验收标准**：修改、删除、替换任意签名范围内的数据，独立核验必须失败。

### 第二批：业务闭环补全（全部 🔧）

P1-4 审计查询接口 → P1-6 Pack 下载 → P1-7 契约对齐 → P1-8 前端 7 个入口 → P1-9 账户体系 → P1-10 文案区分 → P1-11 通知模块 → P1-5 就绪检查

> **验收标准**：一个真实软件项目能完整走完「需求确定 → 交付 → 客户验收 → 异议闭环」。

### 第三批：质量保障（🔧，需先解除测试约定）

P2-5 CI 工作流 → P2-1 单元测试 → P2-2 集成测试 → P2-3 E2E → P2-4 不变量场景全覆盖

> **验收标准**：CI 自动执行测试，关键链路无未解决的 P0/P1 缺陷。

### 第四批：商业部署（🔧 + 🔑）

正式镜像与多架构 → S3 生产驱动 → 备份恢复演练 → Release 与 CHANGELOG → 监控告警 → 合规文档 → 生产域名与 TLS

> **验收标准**：客户可独立安装、升级、备份、恢复。

### 第五批：真实客户试用（⚖️ 🔑）

找 3 家真实软件定制团队 → 跑完 3 个真实交付 → 观察验收门户使用 → 验证付费意愿 → 定价格与售后
